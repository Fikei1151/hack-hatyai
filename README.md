# จำลองน้ำท่วมเมืองหาดใหญ่ · Hat Yai Flood Simulator

เว็บจำลองน้ำท่วมเมืองหาดใหญ่แบบ 3 มิติ สร้างเมืองจากข้อมูลจริง (ภูมิประเทศ อาคาร 91,000+ หลัง ถนน คลอง สถานที่สำคัญ) แล้วใช้สมการน้ำตื้น (shallow water) คำนวณการไหลของน้ำบน GPU ตามฝนและน้ำจากต้นน้ำที่กำหนดเป็นเฟส ๆ จะใช้ข้อมูลจริง (ย้อนเหตุการณ์/พยากรณ์) หรือสุ่มสถานการณ์ก็ได้ ผลการรันถูกเก็บลง Supabase

## เริ่มใช้งาน

```bash
npm install
npm run db:setup          # Supabase local (Docker): start + backup + migration/seed + .env.local — API :56321, Studio :56323
npm run city:build        # ดึงข้อมูลเมืองจาก API จริง → public/city/hatyai (ครั้งแรก ~3–5 นาที, มี cache)
                          # ตัวเลือก (npm run city:build -- …): --north 7200 (โดเมนเดิม), --dem gedtm, --r1-depth 7, --city-share 0.25, --surveyed-bed off
npm run events:build      # ดึงข้อมูลน้ำท่วมจริงปี 2568/2553 → public/city/hatyai/events.json
npm run dev               # http://127.0.0.1:5180
```

`npm run db:setup` สร้าง/อัปเดต `.env.local` ให้อัตโนมัติด้วย URL และ public key ของ local stack (ไม่ใส่ admin key ลง frontend) ต้องเปิด Docker และติดตั้ง Supabase CLI ก่อน
ตรวจฐานข้อมูลด้วย `npm run db:status`, ทดสอบการบันทึกจริงด้วย `npm run db:test`, สำรองตารางแอปด้วย `npm run db:backup` — ดู [คู่มือ local และการย้ายไป VPS](docs/supabase-local.md)
รัน setup ซ้ำได้โดยไม่ reset ข้อมูล; `npm run db:reset` จะล้างข้อมูลเดิม จึงใช้เฉพาะเมื่อตั้งใจเริ่มใหม่
ถ้าไม่ได้เปิด Supabase แอปยังทำงานได้ และบันทึกลงเบราว์เซอร์แทน (มุมขวาบนจะบอกสถานะ)

## ระบบเฟส (Phase)

สถานการณ์หนึ่งประกอบด้วยหลายเฟสเรียงกัน แต่ละเฟสกำหนด:
- ระยะเวลา และช่วงเปลี่ยนผ่าน
- ฝน (มม./ชม. เฉลี่ยทั้งพื้นที่) รูปแบบฝน (ทั่วพื้นที่ / กลุ่มเมฆฝนเคลื่อนที่ / ฝนภูเขา / แนวพายุ) ความแปรปรวน ทิศและความเร็วพายุ
- น้ำไหลเข้าจากต้นน้ำ ณ สิ้นเฟส (คลองอู่ตะเภา 82% + คลองหวะ 15% + คลองวาด 3%) → เฟสต่อกันเป็นกราฟน้ำท่า
- ระดับทะเลสาบสงขลา (น้ำหนุนท้ายน้ำ) ความจุท่อระบายน้ำ การซึมลงดิน
- เหตุการณ์พิเศษ: น้ำล้นตลิ่ง/คันแตก (สุ่มจุดริมคลอง), ท่อระบายน้ำอุดตัน, ทะเลสาบหนุน

ปุ่ม **สุ่มน้ำท่วม** สร้างสถานการณ์ตามคาบการเกิดซ้ำ (2–300 ปี) พร้อมเหตุการณ์สุ่ม (seed เดิมได้ผลเดิม)
ความเร็วเล่น: ⅓x, 1x (= 30 นาทีต่อวินาที), 3x, 10x — แสงอาทิตย์/กลางคืนเดินตามเวลาจริงของสถานการณ์

## แบบจำลองน้ำ

- สมการ shallow water แบบ local-inertial (Bates et al. 2010 / LISFLOOD-FP) + θ-scheme (de Almeida 2012) บน GPU (WebGL2) กริด 20 ม. 720×1,250 เซลล์ (14.4 × 25 กม. ไปจนถึงทะเลสาบสงขลา)
- แรงเสียดทาน Manning ตามสิ่งปกคลุม, porosity ของบล็อกอาคาร, Froude limiter, ก้าวเวลาแบบ CFL อัตโนมัติ
- ฝนเชิงพื้นที่ (กลุ่มเมฆเคลื่อนตามลม), การซึม, ท่อระบายน้ำที่ส่งน้ำกลับเข้าคลอง, ขอบด้านเหนืออยู่ในทะเลสาบสงขลาจริงและใช้ระดับน้ำทะเลสาบเป็นเงื่อนไขขอบ
- ประตูระบายน้ำปากคลอง ร.1 และคลองอู่ตะเภาเข้าเมือง จำกัดอัตราการไหลในร่องคลองตามความจุออกแบบ (แบ่งน้ำเข้า ร.1 / เข้าเมือง)
- พื้นผิวน้ำเคลื่อนไหวตาม **ความเร็วการไหลที่คำนวณได้จริง** (flow mapping): ทิศ/ความเร็วคลื่นและฟองคือผลลัพธ์ของแบบจำลอง
- อาคารที่น้ำท่วมจะเปลี่ยนสีหลังคาตามระดับ (เฝ้าระวัง/อันตราย/วิกฤต) และมีคราบโคลนตามระดับน้ำสูงสุดหลังน้ำลด

(ปากรอ SLA005 + ONE038) ซึ่งสูง 2.0–2.6 ม. ช่วงพีค แทน 1.17 ม. (`scripts/build-events.mjs`)

(RMSE ตลอดเหตุการณ์)
4. **คันที่ 2: ประตูระบายน้ำแบ่งน้ำ** DEM ถ่ายก่อนขยายคลอง ร.1 (2560–64, 465 → 1,200 ลบ.ม./วิ) จึงขุดร่องให้ลึก 7 ม. ตามความจุออกแบบ แล้วใส่ประตูระบายน้ำสองแห่งเป็นหน้าตัดที่จำกัดอัตราการไหลในร่องคลอง ได้แก่ ปากคลอง ร.1 (สูงสุด 1,800 ลบ.ม./วิ ตามที่รับได้จริงปี 68) และคลองอู่ตะเภาเข้าเมือง (สูงสุด 465 ลบ.ม./วิ ปล่อยน้ำคลองหวะ + 25 % ของน้ำอู่ตะเภา ตามสัดส่วน 15–37 % ที่ได้จาก rating ของกรมชลฯ) ส่วนน้ำที่ล้นตลิ่งไหลอ้อมได้อิสระ (ในเหตุการณ์ 2568 กฎปล่อยน้ำเข้าเมืองไม่ได้จำกัดเพิ่ม เพราะร่องคลองรับน้ำได้น้อยกว่านั้นอยู่แล้ว ส่วนปากคลอง ร.1 รับได้จริงราว 600 ลบ.ม./วิ แล้วรับน้ำหลากเพิ่มตามทางจนถึง ~1,800 ลบ.ม./วิ ใกล้ปากคลอง) ผลคือ RMSE ทั้งเหตุการณ์ลดจาก 1.60 เหลือ 0.99 ม. และช่วงน้ำน้อยดีขึ้นมาก (21 พ.ย. จาก 6.75 เหลือ 5.07 ม.) แต่ยอดน้ำลดลงเล็กน้อย
5. **คันที่ 3: ภูมิประเทศ** FABDEM โหลดไม่ได้ (เซิร์ฟเวอร์ data.bris.ac.uk ตอบ 404 ทุกไฟล์ขณะทำ) จึงทดลอง OpenLandMap GEDTM30 v1.2 (CC-BY, `node scripts/build-city.mjs --dem gedtm`) พบว่าในใจกลางเมืองยังเป็นผิวบนอยู่ (ตลาดกิมหยง 16.5 ม. เทียบ Copernicus 17.3 ม.) แต่พื้นที่ชนบทต่ำลงราว 0.4 ม. ทำให้น้ำกระจายมากขึ้นและยอด X.44 ต่ำลง จึงไม่ใช้เป็นค่าเริ่มต้น ที่ใช้แทนคือท้องคลองอู่ตะเภาตามหมุดระดับของสถานี (X.44 −2.2 ม., ONE037 −4.5 ม.) เพราะ DEM เห็นแค่ผิวน้ำ ส่วนสันตลิ่งยังคงจาก DSM

ข้อจำกัดที่ยังเหลือ:
- **ยอด X.44 ยังต่ำกว่าจริง 1.15 ม. และมาเร็วกว่าราว 8 ชม.** ช่วงพีคน้ำในเมืองเกือบเป็นแอ่งราบ (8.6 → 8.2 ม. ใน 3 กม.) ที่ถูกกั้นโดยสันดินห่างไปทางเหนือ 2–3 กม. และ 5–7 กม. ความสูงจริงของคันถนน/ทางรถไฟ สะพาน และคันคลอง ร.1 ยังไม่มีข้อมูลสำรวจ ส่วนเวลาที่ยอดน้ำเข้า (เติมจาก X.173A) ก็อาจเร็วกว่าจริง
- **ช่วงน้ำน้อยยังสูงไป 1–1.3 ม.** (21 พ.ย. 4.92 เทียบ 3.66 ม.) และ **น้ำลดช้า** (28 พ.ย. 7.26 เทียบ 4.99 ม.) เพราะที่ลุ่มทางเหนือระบายลงทะเลสาบได้ช้ากว่าจริง แบบจำลองยังไม่มีคลองย่อยและสถานีสูบน้ำ เช่น สถานีสูบน้ำบางหยีปลายคลอง ร.1 (90 ลบ.ม./วิ)
- **SLA007 บางกล่ำสูงไป 2.7 ม.** น้ำล้นจาก ร.1 เข้าหุบคลองบางกล่ำ เพราะยังไม่มีคันคลอง ร.1
- **ตลาดกิมหยงยังแห้ง** พื้นดินที่ได้จาก DSM อยู่ที่ 9.5 ม. สูงกว่าระดับน้ำในเมือง (~8.7 ม.) ต้องใช้ DTM จาก lidar จึงจะรู้ระดับพื้นจริง

ความเร็ว (Apple M5 Pro, หน้าต่าง 1280×657): กริดใหม่ 720 × 1,250 (900,000 เซลล์ ใหญ่กว่าเดิม 1.7 เท่า) เล่นที่ 1x ได้ 60 fps เต็มความเร็วช่วงต้นเหตุการณ์ ช่วงน้ำสูงสุดเหลือราว 30 fps และ 85–97 % ของความเร็ว 1x ส่วนปุ่ม 10x ถูกจำกัดด้วย GPU เหลือราว 1x (กริดเดิม 720 × 720 ได้ 60 fps ที่ 1x และราว 2.3x เมื่อกด 10x) ถ้าเครื่องช้า สร้างโดเมนเดิม 14.4 × 14.4 กม. ได้ด้วย `node scripts/build-city.mjs --north 7200` (ขอบเหนือกลับไปใช้ rating curve แทนทะเลสาบ)

## ทดลองฝน · พยากรณ์ · ดูทีละวัน

- **🌧️ ทดลองฝน** — เลือกฝน มม./ชม. ระยะเวลา สภาพน้ำในคลอง (ปกติ / เต็มตลิ่ง / น้ำเหนือหลาก) รูปแบบฝน และท่ออุดตันได้ แล้วกด "ให้ฝนตกเลย!" แบบจำลองจะสร้างสถานการณ์ (น้ำเหนือมาเติมคลองก่อน → เมฆก่อตัว → ฝน → ฝนหยุด 6 ชม.) แล้วสรุปพื้นที่ท่วม บ้านน้ำเข้า และจุดลึกสุด พร้อมเก็บประวัติการทดลองไว้เทียบกัน
- **📅 พยากรณ์ & โอกาสน้ำท่วม** — ฝนรายชั่วโมง 10 วันจาก Open-Meteo Ensemble (ECMWF IFS 51 ชุด + NCEP GEFS 31 ชุด) และน้ำท่า GloFAS 51 ชุด (ปรับเทียบกับสถานี X.90 + X.174) โอกาสน้ำท่วมของแต่ละวัน = สัดส่วนชุดพยากรณ์ที่ฝนชั่วโมงใดเกิน 35 มม. หรือทั้งวันเกิน 80 มม. รวมกับสัดส่วนที่น้ำเหนือเกิน 800 ลบ.ม./วิ กดจำลองวันใดวันหนึ่ง (ค่าเฉลี่ย / กรณีฝนหนัก P90) หรือทั้ง 10 วันต่อเนื่องได้ — เป็นการประมาณเพื่อการเรียนรู้ ไม่ใช่ประกาศเตือนภัย
- **📸 ดูทีละวัน** — ปุ่ม ⏩ วันถัดไป เร่งการจำลองไปถึงเที่ยงคืนแล้วหยุด ภาพน้ำ ณ สิ้นแต่ละวันถูกเก็บไว้ กดชิปวันที่บนแถบเวลาเพื่อย้อนดูได้
- ตัวเลข "พื้นที่น้ำท่วม/บ้านน้ำเข้า/ลึกสุด" นับเฉพาะน้ำที่สูงเกินขอบแอ่งธรรมชาติ (นา บ่อ แก้มลิง ที่ priority-flood คำนวณได้จาก DEM) จึงไม่นับบ่อที่แค่มีน้ำเต็ม

**เครื่องผู้เล่น (ข้อจำกัดจริงของงานนี้)** ต้องมี WebGL2 + float render target (`EXT_color_buffer_float`) ซึ่งเบราว์เซอร์ทั่วไปรองรับ ~97–99% (Chrome/Edge/Firefox ใหม่, Safari/iOS 15+) บน M5 Pro ของเครื่องพัฒนา 1 รอบเกม (น้ำ 4 ชม.) ใช้ราว 6–15 วินาที; GPU ที่ช้ากว่า 10 เท่า (ประมาณการ ยังไม่ได้ทดสอบบนเครื่องจริง) จะใช้ราว 1 นาทีต่อรอบ และมือถือรุ่นล่างอาจไม่ไหว — หน้าตั้งค่าเกมวัดความเร็วเครื่องแล้วบอกเวลาต่อรอบให้ผู้เล่นรู้ล่วงหน้า ถ้าจะรองรับมือถือจริงจัง ทางออกคือกริดหยาบกว่า (40 ม. เร็วขึ้น ~8 เท่า) หรือคำนวณพายุสำเร็จรูปไว้ล่วงหน้า (น้ำไม่ขึ้นกับการเล่นของผู้เล่น จึงอบเก็บเป็นไฟล์ได้)

**Supabase** (ไม่จำเป็นต่อการเล่น — ถ้าเชื่อมไม่ได้เกมเก็บผลในเบราว์เซอร์) แผนฟรี: DB 500 MB, egress 5 GB + 5 GB (cache) ต่อเดือน, **พักโปรเจกต์เมื่อไม่มีการใช้งาน 7 วัน**, Realtime 200 การเชื่อมต่อ (แอปยังไม่ใช้) เกมหนึ่งเกมเขียน ~1 KB อ่านอันดับ 8 แถว → น้อยมาก **ก่อนเปิดสาธารณะต้องแก้ RLS**: ตาราง `scenarios` `phases` `simulation_runs` `weather_cache` ยังเป็น "prototype open access" (คนถือ anon key ซึ่งอยู่ในโค้ดฝั่งเบราว์เซอร์ ลบ/แก้ได้หมด หรือเขียนขยะจนเต็ม 500 MB) — เปลี่ยนเป็นอ่านอย่างเดียว หรือผูกกับการล็อกอิน; `game_results` จำกัดแค่อ่าน/เพิ่มและตรวจขนาดแล้ว แต่ยังไม่มี rate limit (ถ้าจะกันสแปมต้องผ่าน Edge Function)

**API ภายนอก** (เรียกจากเบราว์เซอร์ผู้เข้าชม นับโควตาตาม IP ของแต่ละคน): Open-Meteo ฟรีสำหรับ *ไม่แสวงกำไร* เท่านั้น (600/นาที, 5,000/ชม., 10,000/วัน; ถ้ามีโฆษณา/ค่าสมาชิกต้องซื้อแผน) แท็บพยากรณ์ใช้ ~6 คำขอต่อผู้เข้าชม · ThaiWater ไม่พบเงื่อนไข/ลิมิตที่ประกาศไว้ (ยังไม่ได้ยืนยัน) · ต้องใส่เครดิตข้อมูล (ODbL, Copernicus, Open-Meteo CC BY 4.0 — มีอยู่ท้ายหน้าแล้ว)

**เช็กลิสต์ก่อนขึ้นจริง**: `npm run build` → เสิร์ฟ `dist/` · ใส่ `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` ของโปรเจกต์จริง (หรือไม่ใส่ = โหมดออฟไลน์) · รัน migration ทั้งหมดใน `supabase/migrations` + seed `places.sql` · แก้ RLS ตามข้างบน · อย่าใช้ SPA fallback (ไฟล์เมืองที่หายจะกลายเป็น 200 + HTML) · ถ้าจะลดการดาวน์โหลดครั้งแรกจาก ~16 MB เหลือ ~8 MB: โหลดต้นไม้/ภาพละเอียดทีหลัง, แปลง JPEG เป็น WebP/AVIF, เก็บ `terrain.f32` แบบ 16 บิต

## ฐานข้อมูล (supabase/migrations)

| ตาราง | เก็บอะไร |
|---|---|
| `scenarios`, `phases` | สถานการณ์และเฟส (บันทึกผ่าน RPC `save_scenario` แบบ transaction เดียว) |
| `simulation_runs` | ผลแต่ละรอบ: ค่าสูงสุด, จุดสำคัญ, กราฟเวลา |
| `places` | สถานที่สำคัญจาก OSM 572 แห่ง 14 หมวด (seed: `supabase/seeds/places.sql`) มีคอลัมน์ PostGIS `geog` + ฟังก์ชัน `places_near(lat, lon, radius_m)` |
| `run_place_impacts` | ความลึกสูงสุดและเวลาที่น้ำถึงของแต่ละสถานที่ในแต่ละรอบ |
| `weather_cache` | cache ผลจาก Open-Meteo/ThaiWater และพยากรณ์ ensemble (3 ชม.) |
| `game_results` | ผลเกมกระดาน (ทีม คะแนน ดาว ฉาก) — แอปอ่าน/เพิ่มได้อย่างเดียว ไม่มีนโยบายแก้/ลบ |

นโยบาย RLS ตอนนี้เปิดให้ anon เขียนได้ (ต้นแบบในเครื่อง) — ต้องปรับก่อนเปิดใช้งานจริง
